# Workflow Node Authoring Kit

Status: **phase 2 backend implemented** · Scope:
`lib/hermitscale/workflows/nodes/**`, `lib/hermitscale/integrations/**`

This document designs the kit for authoring catalog nodes in the new workflow
engine. The engine's hard problems — durable execution (Runic + event-sourced
`Run`/`RunEvent` + leases), per-node retry/timeout policy, `{id, version}`
versioning, and editor-grade graph validation — are already solved. What is not
yet designed is the **node-authoring surface**: the contract every node module
implements, and the small set of primitives that keep that contract clean as the
catalog grows from 4 nodes to 100.

The goal is **clean primitives, not a framework.** Each primitive should be
greppable, individually testable, and explainable in one sentence.

---

## 1. Principles

1. **A node is a pure description plus a pure builder.** `spec/0` is static
   metadata; `build/2` is a pure function from validated params + wiring context
   to a Runic component. No I/O, no process state at author time. All runtime
   effects live inside the closure Runic executes.

2. **Validate and normalize params exactly once, at the graph boundary.** Nodes
   never see raw, string-keyed, untyped JSON. By the time `build/2` runs, params
   are validated, defaulted, and atom-keyed. This single decision removes the
   dual-key (`Map.get(c, "url") || Map.get(c, :url)`) and string-fetch
   (`Map.fetch!(params, "method")`) noise that accreted in the old engine.

3. **Declared inputs are the wiring contract.** A node's `inputs` list *is* its
   port specification. For a join, the list length is the builder's arity and
   the list order is the slot order. There is no separate "ports" concept and no
   "capability token" concept — a node that depends on the output of other nodes
   (an AI agent depending on a model node, a tools node, a schema node) is simply
   a `:join` with named inputs. See §6.

4. **Control flow is expressed by `kind`, not by return values.** The old engine
   leaked control flow into magic return tuples (`{:skip, reason}`,
   `{:branch, name, data}`, `{:sleep, ms, input}`). Here, conditional execution
   is a `:rule`, fan-out is a `:map`, fan-in is a `:reduce`/`:join`. Builders
   return Runic components; they never invent runtime protocol.

5. **Let it crash; policy decides the rest.** A builder's closure raises on
   failure. Whether that halts the run, skips the node, or retries with backoff
   is the per-node `policy` in the graph (already implemented in `Compiler` and
   `Validator`). Nodes do not implement retry, do not swallow errors, and do not
   return `{:error, _}` as control flow.

6. **Runtime dependencies are declared, not discovered.** A node that needs a
   credential or any other ambient value declares it. The engine injects it via
   Runic's `context/1,2`, and `Runic.Workflow.required_context_keys/1` surfaces
   the full set for a workflow (drives the editor's credential pickers).

## 2. The contract

One behaviour, defined alongside the authoring macro in
`Hermitscale.Workflows.Nodes.Behaviour` (we keep the existing module name —
`Node` is a live Elixir/Erlang module for distributed nodes, so it's reserved in
practice and confusing even when namespaced):

```elixir
defmodule Hermitscale.Workflows.Nodes.Behaviour do
  @moduledoc """
  Defines a workflow catalog node: declarative metadata plus a `build/2`
  that emits a Runic component. `use Hermitscale.Workflows.Nodes.Behaviour`
  generates a compile-time-validated `spec/0` and `__catalog_node__/0`.
  """

  @type kind :: :step | :join | :map | :reduce | :rule

  @type spec :: %{
          id: String.t(),
          version: pos_integer(),
          kind: kind(),
          inputs: [atom(), ...],
          outputs: [atom(), ...],
          params_schema: keyword(),
          requires: keyword(),
          default_policy: map(),
          deprecated: boolean()
        }

  @type ctx :: %{name: String.t(), inputs: [String.t()]}

  @doc "Static node description. Generated by `use`."
  @callback spec() :: spec()

  @doc "Builds a Runic component from validated params and wiring context."
  @callback build(params :: map(), ctx :: ctx()) :: term()

  @doc "Optional cross-field param validation beyond the NimbleOptions schema."
  @callback validate_params(params :: map()) :: :ok | {:error, String.t()}

  @optional_callbacks validate_params: 1
end
```

`build/2` receives:

- `params` — a validated, atom-keyed map (defaults applied). See §5.
- `ctx` — `%{name: id, inputs: parent_ids}` where `name` is the node's graph id
  (used as the Runic component name) and `inputs` are the upstream node ids in
  slot order.

`validate_params/1` is the home for rules the declarative schema can't express
("`operand` is required when `operation` is binary"). The validator calls it; if
absent, only the schema runs.

## 3. The `use` macro

The current `spec/0` is a hand-written map repeated in every node. It is
explicit (good) but unvalidated (a typo'd `kind:` or malformed schema is only
caught at runtime, if at all). The macro keeps the declaration flat and explicit
while validating it **at compile time**:

```elixir
defmodule Hermitscale.Workflows.Nodes.HttpRequest.V2 do
  use Hermitscale.Workflows.Nodes.Behaviour,
    id: "http_request",
    version: 2,
    kind: :step,
    inputs: [:main],
    outputs: [:main],
    requires: [credentials: []],
    params: [
      method: [type: {:in, ~w(GET POST PUT PATCH DELETE)}, required: true, doc: "HTTP method."],
      url: [type: :string, required: true, doc: "URL template."]
    ]

  require Runic
  alias Hermitscale.{HTTP, Workflows.Template}

  @impl true
  def build(%{method: method, url: url_template}, ctx) do
    Runic.step(
      fn input ->
        url = Template.render!(^url_template, input)
        auth = context(:credentials, default: nil)

        case HTTP.request(^method, url, body: input, auth: auth) do
          {:ok, response} -> response.body
          {:error, reason} -> raise "HTTP request failed: #{inspect(reason)}"
        end
      end,
      name: ctx.name
    )
  end
end
```

Note what disappeared versus today's `v2.ex`: the `@params_schema NimbleOptions.new!(...)`
attribute, the `def spec do %{...} end` block, and the `Map.fetch!(params, "method")`
string access. The builder pattern-matches typed params straight out of the head.

The macro itself is intentionally thin — every option maps directly to a spec
field, no derivation magic (we do **not** infer `version` from the module name;
explicit beats clever):

```elixir
defmacro __using__(opts) do
  spec = Hermitscale.Workflows.Nodes.Behaviour.__compile_spec__!(opts, __CALLER__.module)

  quote do
    @behaviour Hermitscale.Workflows.Nodes.Behaviour
    @__node_spec__ unquote(Macro.escape(spec))

    @impl true
    def spec, do: @__node_spec__
    def __catalog_node__, do: @__node_spec__
  end
end

@doc false
def __compile_spec__!(opts, module) do
  id = require_opt!(opts, :id, module)
  version = require_opt!(opts, :version, module)
  kind = require_opt!(opts, :kind, module)
  inputs = Keyword.get(opts, :inputs, [:main])
  outputs = Keyword.get(opts, :outputs, [:main])

  assert!(kind in ~w(step join map reduce rule)a, module, "invalid kind #{inspect(kind)}")
  assert!(is_binary(id), module, "id must be a string")
  assert!(is_integer(version) and version > 0, module, "version must be a positive integer")
  assert!(ports?(inputs), module, "inputs must be a non-empty list of atoms")
  assert!(ports?(outputs), module, "outputs must be a non-empty list of atoms")

  %{
    id: id,
    version: version,
    kind: kind,
    inputs: inputs,
    outputs: outputs,
    # NimbleOptions.new!/1 raises here, at compile time, on a malformed schema.
    params_schema: NimbleOptions.new!(Keyword.get(opts, :params, [])).schema,
    requires: Keyword.get(opts, :requires, []),
    default_policy: Keyword.get(opts, :default_policy, %{}),
    deprecated: Keyword.get(opts, :deprecated, false)
  }
end

defp ports?(list), do: is_list(list) and list != [] and Enum.all?(list, &is_atom/1)
```

`params:` is a plain NimbleOptions schema — no bespoke field DSL to learn, and it
still projects to JSON Schema for the editor through the existing
`Workflows.JsonSchema.from_nimble/1`. `Catalog` is unchanged: it still discovers
modules by `__catalog_node__/0`.

## 4. Kinds map one-to-one to Runic primitives

| `kind`     | Runic constructor              | Builder shape                                  | Use for |
|------------|--------------------------------|------------------------------------------------|---------|
| `:step`    | `Runic.step/2`                 | `fn input -> out end`                          | transforms, actions, single-input work |
| `:join`    | `Runic.step/2` (n-arity fn)    | `fn a, b, … -> out end` (arity = `length(inputs)`) | combine several upstream outputs |
| `:map`     | `Runic.map/2`                  | `fn item -> out end`                           | fan-out over a collection |
| `:reduce`  | `Runic.reduce/3`               | `acc, fn item, acc -> acc end`                 | fan-in / accumulate |
| `:rule`    | `Runic.rule/1,2`               | `given`/`where`/`then`                          | conditional execution & branching |

This table is the entire control-flow vocabulary. The old engine's `condition`,
`switch`, `wait`, `splitter`, `aggregator`, and `join` builtins collapse into
these five kinds plus per-node `policy`:

- **`condition` / `switch`** → `:rule`. The `where` clause is the predicate; the
  branch is just which downstream nodes are connected. No `{:skip, _}` /
  `{:branch, _, _}` tuples.
- **`splitter`** → `:map`. No "fan-out via list-of-facts" convention.
- **`aggregator` / `join`** → `:reduce` / `:join`.
- **`wait`** → a `policy` concern (`deadline_ms` / a future `delay_ms`), not a
  node returning `{:sleep, ms, input}`.

## 5. Params: validate-and-cast-once

Raw graph params are string-keyed JSON. Exactly one module turns them into clean
atom-keyed maps, and it is shared by both the validator (editor feedback) and the
compiler (build input) so the two can never diverge:

```elixir
defmodule Hermitscale.Workflows.Nodes.Params do
  @moduledoc """
  Validates and normalizes raw graph params against a node's NimbleOptions schema.
  """

  @doc """
  Casts string-keyed JSON params into a validated, atom-keyed map.

  Only schema-declared keys are considered. Atoms come from the schema's known
  field set, so this never calls `String.to_atom/1` on user input.
  """
  def cast(raw, schema) when is_map(raw) do
    options =
      for {field, _opts} <- schema,
          key = Atom.to_string(field),
          Map.has_key?(raw, key) do
        {field, Map.fetch!(raw, key)}
      end

    case NimbleOptions.validate(options, schema) do
      {:ok, validated} -> {:ok, Map.new(validated)}
      {:error, %NimbleOptions.ValidationError{} = error} -> {:error, error}
    end
  end

  def cast!(raw, schema) do
    case cast(raw, schema) do
      {:ok, params} -> params
      {:error, error} -> raise ArgumentError, Exception.message(error)
    end
  end
end
```

`Compiler.do_compile/2` casts before `build/2`:

```elixir
spec = module.__catalog_node__()
params = Params.cast!(node_spec["params"] || %{}, spec.params_schema)
node = module.build(params, %{name: id, inputs: node_parents})
```

`cast!` is safe here because `Validator.validate/1` has already run (the compiler
is only reached for valid graphs). `Validator.params_issues/3` is refactored to
call `Params.cast/2` instead of duplicating the `options`-building loop it
contains today — one source of truth for "what are this node's params."

## 6. Ports, wiring, and the "sub-node inputs" pattern

`inputs` and `outputs` are the node's ports. For most nodes `inputs: [:main]`.
For a join, the list defines arity and slot order:

```elixir
# merge_decision/v1.ex
use Hermitscale.Workflows.Nodes.Behaviour, id: "merge_decision", version: 1,
  kind: :join, inputs: [:left, :right], outputs: [:main]

def build(_params, ctx) do
  Runic.step(fn left, right -> %{left: left, right: right} end, name: ctx.name)
end
```

The names (`:left`, `:right`) document intent and drive
`Validator`'s join-arity / slot checks (already implemented: it requires
contiguous, unique `to_input` slots `0..n-1`). The actual wiring is positional —
`Compiler.parent_map/1` orders parents by `to_input`, and Runic maps positional
parents to positional builder arguments.

**This is the whole story for "AI agent" nodes.** An agent that needs a model, a
tool set, and a structured-output schema is a join whose inputs are fed by
ordinary upstream nodes:

```elixir
use Hermitscale.Workflows.Nodes.Behaviour, id: "ai_agent", version: 1,
  kind: :join,
  inputs: [:main, :model, :tools, :schema],
  outputs: [:main],
  requires: [credentials: []],
  params: [system_prompt: [type: :string, default: ""]]

def build(%{system_prompt: prompt}, ctx) do
  Runic.step(
    fn message, model, tools, schema ->
      creds = context(:credentials)
      AI.chat(model, message, tools: tools, schema: schema, system: ^prompt, auth: creds)
    end,
    name: ctx.name
  )
end
```

`:model`, `:tools`, `:schema` are produced by their own plain `:step` nodes and
connected into slots 1/2/3. There is no special token type, no `provides`/`accepts`
matching, no capability registry — the graph connection *is* the dependency. (The
editor can still type-hint which node kinds are sensible to connect into each
slot, but that's an editor affordance, not an engine concept.)

## 7. Runtime context

A node reaches ambient runtime values — credentials, tenant ids, feature flags —
through Runic's `context/1,2` inside its closure, and declares what it needs in
`requires:` (a keyword list):

```elixir
requires: [credentials: []]
# ...
token = context(:credentials)
api_base = context(:api_base, default: "https://api.example.com")
```

Two properties make this clean:

1. **Per-node scoping.** `Runic.Workflow` resolves `context(:key)` against
   `run_context[node_name]` merged over a `:_global` map (`workflow.ex:420`). Two
   nodes can both read `context(:credentials)` and get *different* values — each
   its own. This is what lets one workflow mix nodes from different providers
   with no special handling.
2. **Introspectable.** `Runic.Workflow.required_context_keys/1` reports every
   `context/1` key per node, and `validate_run_context/2` fails fast if the run
   isn't started with them. `requires:` is the design-time declaration of the
   same need; a future `@after_compile` check can assert the two agree (§14).

`requires:` also drives editor affordances (e.g. a credential picker) and
documents intent. Credentials are the principal use of this mechanism and get
their own section next.

## 8. Credentials

Credentials are the principal runtime dependency and the easiest thing to get
wrong, so they get a dedicated contract. The governing rule: **the graph stores
references, never secrets.** A node says "I need a Google credential with these
scopes"; the token is resolved at run start and injected per node via §7's
context mechanism. Nodes contain no auth plumbing.

### 8.1 The model: references, not secrets

A workflow graph is user-editable JSON that we persist, version, and project to
an editor — it must never contain a secret. What it stores is a **credential
reference**: an opaque pointer to a secret held elsewhere.

```json
{
  "provider": "google.oauth",
  "credential_id": "cred_01H...",
  "owner": "user_01H..."
}
```

The secret (OAuth access + refresh tokens, or an API key) lives in the secrets
store, keyed by `credential_id`. The reference is safe to persist in the graph,
log, and render in the editor; the secret is not, and never leaves the
resolution path in §8.4.

### 8.2 Declaring a credential need

A node declares the requirement in `requires:` (§7); the value names the provider
and the scopes the operation needs:

```elixir
requires: [credentials: []]                                          # any credential (generic HTTP)
requires: [credentials: [provider: "google.oauth", scopes: [...]]]   # a specific provider + scopes
```

- `provider` constrains which credentials the editor offers and which `Provider`
  resolves the token. Omit it (a generic HTTP node) and the editor offers any
  bearer/basic credential.
- `scopes` are per *operation* — `read_rows` asks for `…/spreadsheets.readonly`,
  `append_row` for `…/spreadsheets`. They drive the OAuth consent screen (§8.5).

For integration nodes the `use` macro injects `provider`, so the node states only
`scopes:` (§12.2).

### 8.3 The `Provider` contract

One behaviour owns the reference → token seam. It lives in the integrations tree
with its own code-first `persistent_term` index (mirroring `Catalog` — one
registry, no module/map duplication), and is **separate from the node catalog**:

```elixir
defmodule Hermitscale.Integrations.Provider do
  @callback provider_id() :: String.t()

  @doc "Resolves a stored credential reference into an access token for the given scopes."
  @callback fetch_token(ref :: map(), scopes :: [String.t()]) ::
              {:ok, %{access_token: String.t(), expires_at: DateTime.t() | nil}}
              | {:error, term()}

  @doc "Egress allowlist for this provider's API hosts."
  @callback network_domains() :: [String.t()]
end
```

- **OAuth providers** (`Google.OAuth`) hide the refresh dance behind
  `fetch_token/2`: check expiry, refresh if stale, return a live access token.
- **API-key providers** ignore `scopes` and return the stored key as the token.
- `network_domains/0` is the egress allowlist for the provider's hosts (§8.6).

Nodes never call a `Provider` — only the run-start resolver (§8.4) does.

### 8.4 Resolution and injection

The control plane resolves credentials once, at run start, and hands Runic a
ready run context:

1. Walk the graph's credentialed nodes. For each, take its bound reference and
   declared scopes and call `Provider.fetch_token(ref, scopes)`.
2. Build `run_context = %{node_id => %{credentials: token}}` — keyed by node id,
   so each node gets exactly its own token (§7's per-node scoping).
3. `Runic.Workflow.validate_run_context/2` pre-flights that every required key is
   present **before** execution begins — a missing or unresolvable credential
   fails the run up front, not mid-flight.
4. At run time, `context(:credentials)` inside each node's closure returns that
   node's token.

A token resolved at run start is held for the run's duration; re-resolution for
durable runs that outlive token expiry is a known gap (§14).

### 8.5 Binding and scopes (editor)

Binding granularity is **shared per provider per workflow, with a per-node
override**: a user picks their Google account once and every Google node uses it,
unless a specific node is overridden to a different account. The editor computes
the **union of scopes** across all of a provider's nodes to request a single
consent covering the whole workflow.

### 8.6 Security invariants

- **Secrets never enter the graph, events, or logs.** `Run`/`RunEvent` persist
  inputs and outputs; credential tokens must be excluded from anything written
  there.
- **References are opaque.** A `credential_id` discloses nothing; authorization
  to resolve it is checked at run start against the run's owner.
- **Egress is constrained.** `Provider.network_domains/0` is the allowlist a
  credentialed node's HTTP client should be pinned to, so a compromised URL
  template can't exfiltrate a token to an arbitrary host.

## 9. Errors and control flow

- **Failure:** raise inside the closure. `policy.on_failure` (`halt` | `skip`) and
  the retry/backoff keys (already compiled in `Compiler.normalize_policy/1`)
  decide the consequence. Nodes contain no `try/rescue`, no fallback values, no
  `{:error, _}`-as-control-flow. (Run the repo's `elixir-let-it-crash-audit`
  skill against the nodes dir periodically to keep this honest.)
- **Conditional execution:** a `:rule` whose `where` clause gates the `then`
  reaction. Downstream wiring expresses the branches.
- **Skip-as-intent vs. skip-as-failure:** these are different. "Condition didn't
  match, so this branch doesn't run" is a `:rule` not firing — normal. "Node
  crashed and policy says skip" is `policy.on_failure: skip`. Keeping them in
  separate mechanisms is the point.

## 10. Versioning and deprecation

Already a strength of the engine; the kit just sets conventions:

- One module per version: `nodes/<id>/v<n>.ex` →
  `Hermitscale.Workflows.Nodes.<Id>.V<n>`. `Catalog` keys on `{id, version}` and
  raises on duplicates.
- A breaking change to params or behaviour is a **new version module**, not an
  edit. The prior version stays, with `deprecated: true`, until no stored graph
  references it. `Validator` already emits a `:deprecated_catalog_node` warning.
- Graphs always pin `{type, version}`, so old runs stay reproducible.

## 11. Testing nodes

A node is a pure builder, so a test builds the component and runs it through a
one-node Runic workflow:

```elixir
defmodule Hermitscale.Workflows.Nodes.HttpRequest.V2Test do
  use ExUnit.Case, async: true

  alias Hermitscale.Workflows.Nodes.HttpRequest.V2
  alias Hermitscale.Workflows.Nodes.Params

  test "spec is well-formed and discoverable" do
    spec = V2.spec()
    assert spec.id == "http_request" and spec.version == 2
    assert spec.kind == :step
    assert Keyword.has_key?(spec.requires, :credentials)
  end

  test "casts params and renders the url template at runtime" do
    params = Params.cast!(%{"method" => "GET", "url" => "https://x.test/{{ $.id }}"}, V2.spec().params_schema)
    step = V2.build(params, %{name: "fetch", inputs: []})
    # drive `step` through Runic with a stubbed Hermitscale.HTTP and assert on the emitted fact
  end
end
```

Conventions from `AGENTS.md` apply: `async: true`, `start_supervised!/1` for any
process, no `Process.sleep/1`. Each node ships with a sibling `_test.exs`;
`test/support/fixtures/` holds shared graph fixtures.

## 12. Integrations (Google, Slack, …)

Large integrations like Google span several products (Gmail, Sheets, Docs,
Drive, Slides), dozens of actions, a shared OAuth provider, and per-product API
clients. The old engine modelled this with a first-class `Integration` behaviour
(`actions/0`, `triggers/0`, `step_modules/0`), *two* registries (module-based +
serialized-map), and a hand-maintained `Manifest`. That machinery was the bulk
of its cruft. We don't reproduce any of it.

**Stance: an "integration" is a code-organization + shared-runtime convention,
not a catalog entity.** The catalog stays flat — a Google action is just a node,
discovered by `{id, version}` like any other. "Google" is exactly two things: a
*namespace* for node ids and directories, and a *shared-code module tree* that
nodes lean on. The engine never learns that "Google" exists.

### 12.1 Two trees

```
lib/hermitscale/workflows/nodes/google/        # catalog nodes ({id, version})
  sheets/append_row/v1.ex     id: "google.sheets.append_row"
  sheets/read_rows/v1.ex      id: "google.sheets.read_rows"
  gmail/send_email/v1.ex      id: "google.gmail.send_email"

lib/hermitscale/integrations/google/           # NOT in the catalog — shared code
  oauth.ex                    # credential provider: ref -> token (+ refresh)
  sheets/client.ex            # Req-based API client: base URL, pagination, errors
  gmail/client.ex
  sheets/resolvers.ex         # dynamic "pick a spreadsheet" dropdown resolvers
```

The split is load-bearing. `Catalog.refresh!/0` discovers every module exporting
`__catalog_node__/0`, so shared code **must** live outside `nodes/`. Housing it
under a top-level `Hermitscale.Integrations.*` tree (rather than under
`Workflows.*`) keeps the workflow engine vendor-agnostic: nodes call library
code; the engine has no vendor knowledge.

Node ids are dotted and namespaced — `google.sheets.append_row`. The id is just
a string key in the catalog (no pattern is enforced on `spec.id`), so dots are
free and read well. (This is distinct from a *graph instance* id, which the
validator constrains via `@node_id_pattern`.)

### 12.2 The per-integration `use` macro

The old engine's worst per-action tax was boilerplate: every action re-declared
its credential field, retry policy, and provider. We kill that with a thin,
transparent wrapper macro — **not** a framework, just a keyword merge over the
base behaviour:

```elixir
defmodule Hermitscale.Integrations.Google do
  @moduledoc "Shared definitions for Google catalog nodes."

  @provider "google.oauth"
  @default_policy %{backoff: "exponential", max_retries: 3, timeout_ms: 30_000}

  defmacro __using__(opts) do
    {scopes, opts} = Keyword.pop(opts, :scopes, [])

    quote do
      use Hermitscale.Workflows.Nodes.Behaviour,
        unquote(
          opts
          |> Keyword.put(:requires, credentials: [provider: @provider, scopes: scopes])
          |> Keyword.put_new(:default_policy, @default_policy)
        )
    end
  end
end
```

- `provider` is constant for the integration, so it's injected, never repeated.
- `scopes` vary per operation (read-only vs. read-write), so they stay at the
  call site and flow into the credential requirement.
- `default_policy` gives the integration a sane retry/timeout baseline that a
  graph's per-node `policy` still overrides (see §12.3).

The credential requirement the macro injects, and how the bound reference becomes
a live token at run start, is the dedicated **Credentials** section (§8).

A node then reads as pure intent — params in, client call out, zero auth
plumbing:

```elixir
defmodule Hermitscale.Workflows.Nodes.Google.Sheets.AppendRow.V1 do
  use Hermitscale.Integrations.Google,
    id: "google.sheets.append_row",
    version: 1,
    kind: :step,
    scopes: ["https://www.googleapis.com/auth/spreadsheets"],
    params: [
      spreadsheet_id: [type: :string, required: true, doc: "Target spreadsheet."],
      range: [type: :string, default: "Sheet1!A:Z", doc: "A1 range to append after."]
    ]

  require Runic
  alias Hermitscale.Integrations.Google.Sheets.Client

  @impl true
  def build(%{spreadsheet_id: id, range: range}, ctx) do
    Runic.step(
      fn input -> Client.append(context(:credentials), ^id, ^range, input) end,
      name: ctx.name
    )
  end
end
```

### 12.3 Policy inheritance

`default_policy` from the integration macro is the baseline; the graph's per-node
`policy` (already compiled by `Compiler.normalize_policy/1`) overrides key by
key. Resolution order, applied in the compiler: `node policy` ▸
`integration default_policy` ▸ engine default. This is the clean replacement for
the old engine's `@retry_policy` copied into every action.

### 12.4 Deferred to later phases

The node kit does not block any of these; they are called out so the seams stay
clean:

- **Resolvers** (`sheets/resolvers.ex`) — `resolve(%{query, params, credentials})
  -> {:ok, [option]}` modules referenced from a param's editor metadata, for
  dropdowns like "pick a spreadsheet". They need credentials too, resolved via
  the same bound ref but at *edit* time rather than run time — a distinct
  resolution path to design (§14).
- **Triggers** (Gmail "new email", Sheets "new row") — Oban-driven polling. Open
  question whether these are a sixth `kind` carrying `registration_spec/2` +
  `normalize_event/2`, or a concept outside the graph. See §14.
- **API-key providers** — the `Provider` behaviour already covers them
  (`fetch_token/2` ignores scopes for an API key); only the editor's picker
  differs.

## 14. Open questions

1. **Dynamic specs.** A few node types (e.g. a manual-input trigger whose output
   schema is user-defined) want a params-derived schema. Add an optional
   `effective_spec/1` callback, or keep specs static and model variability as
   params? Leaning static for v1.
2. **`requires` vs. `context` drift.** Worth an `@after_compile` check that the
   declared `requires` matches the `context/1` keys Runic extracts from the
   closure?
3. **Output typing.** Do we want `outputs` to carry a schema (for editor
   connection validation), or keep them as bare port names for now?
4. **Triggers as a kind.** Are Gmail/Sheets/schedule triggers a sixth `kind`
   carrying `registration_spec/2` + `normalize_event/2`, or a concept outside the
   graph that *produces* a run? Leaning outside-the-graph (an Oban-driven
   producer), since a trigger isn't a Runic component.
5. **Resolver credential resolution.** Edit-time resolvers ("pick a spreadsheet")
   need a token from the bound credential ref *before* a run exists. That's a
   second resolution path (LiveView/editor context, not run context) — shares
   `Provider.fetch_token/2` but not the `run_context` plumbing.
6. **Credential ref override UX.** Shared-per-provider binding with per-node
   override is the model; the editor representation of an override (and how it
   surfaces in the graph JSON) is undesigned.
7. **Token expiry on durable runs.** Credentials are resolved once at run start
   (§8.4). A durable run that outlives its access token needs re-resolution —
   re-fetch on a step boundary, or refresh lazily inside `Provider`? Out of scope
   for sync/short runs; must be designed before durable runs use credentials.
