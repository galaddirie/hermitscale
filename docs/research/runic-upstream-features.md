# Runic upstream features: independent assessment

Research date: 2026-10-11. Comparison target: upstream Git commit `6e6373832c00aa9ec5d19faeae945b61e2db50b1`, versus this workspace's `vendor/runic` (`0.1.0-alpha.8` plus application patches). Additional target: open PR #43 at `d1cd8c6863e89d9742bcd54af44c95097064ce4d`. Scope: public features, source/test evidence, relevance, and limitations. No application or vendor changes were made. Unless specifically identified as a locally executed check, reading a regression test is evidence of intended coverage, not a claim that it passed here.

## Main is ahead of the published package

The [Hex package](https://hex.pm/packages/runic) and [release API](https://hex.pm/api/packages/runic/releases/0.1.0-alpha.11) report `0.1.0-alpha.11`, published `2026-09-17T20:00:34Z`. The pinned Git source [also reports alpha.11](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/mix.exs#L5). I downloaded the official [Hex tarball](https://repo.hex.pm/tarballs/runic-0.1.0-alpha.11.tar) in memory and compared selected contents: `Connection` and `Identity` match main, while `SingleOutput` and `TaskScope` are absent and Runner, Worker, and SchedulerPolicy differ. Therefore version strings cannot identify the newer runtime behavior. Pin the examined revision for an upgrade experiment. The changelog's upgrade section still claims the application reports alpha.9, so it is not a complete current release map.

## Ranked shortlist

### 1. Named-port connections and explicit workflow boundaries

**New relative to our vendor; present in published alpha.11.** `Workflow.add(component, connections: [...])` accepts durable connections specifying source component/output, target input, a safe selector path, and an assembly target path. Upstream validates the complete group and lowers it into InputBinding and, where needed, Join nodes. Input ordering comes from declared target ports rather than connection declaration order. Paths contain data segments, never executable callbacks. Sources with one declared output expose their entire value; several outputs select fields/positions from one domain value, which does not automatically mean independently emitted output facts. Evidence: [Connection contract](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/connection.ex#L1), [InputBinding execution](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/input_binding.ex#L61), [lowering/replay/validation tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/workflow/named_connection_test.exs#L20).

**Hermitscale value:** much of the current parent-list/join reconstruction in [Compiler](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows/compiler.ex:146) and [Nodes.Behaviour](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows/nodes/behaviour.ex:103) could become declared data bindings. The existing expression language still needs application handling for computed expressions and ambient namespaces; selectors only replace direct safe path projection. Avoid generating new atoms from arbitrary editor names: port names are atoms, so use a fixed declared vocabulary or a validated mapping.

Reusable workflows can now declare input/output boundary ports and preserve nested definitions/build logs through replay. This is a useful seam for reusable integration subflows, with the application retaining versioned authoring JSON. [Definition](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/definition.ex#L1) deliberately excludes runtime facts, context, hooks, and runnable state. Ports without explicit `to`/`from` can be contract-only; do not expect inferred internal ownership. [Nested boundary tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/workflow/composite_connection_boundary_test.exs#L17) cover construction replay and named connections.

### 2. SingleOutput for domain-specific integration nodes

**New on main; absent from published alpha.11.** `use Runic.Workflow.SingleOutput` gives an ordinary custom component the same prepare/execute/apply lifecycle as Step: hooks, causal child Facts, activation consumption, and collection tracking. The application supplies `run(component, input, context)` and returns explicit `Result.value(data, metadata: ...)` or `Result.failure(reason)`. Custom identity, ports, and reconstruction still require the Component protocol; SingleOutput does not replace it. [Implementation](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/single_output.ex#L1), [callback context](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/single_output/context.ex#L1), [explicit Result semantics](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/single_output/result.ex#L1).

**Hermitscale value:** explicit reusable HTTP/Google Sheets component representations can preserve structured provider errors for retry classification instead of turning them into generic strings, as [HTTP V2](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows/nodes/builtin/http_request/v2.ex:29) and [AppendRow V1](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows/nodes/google/sheets/append_row/v1.ex:20) currently do. Pure transformation nodes can remain Steps; replacing every Step would add complexity without benefit.

Important boundaries: ordinary Step `{:error, reason}` is still successful data; explicit failure conversion is opt-in. Output metadata replaces rather than automatically merges input metadata, and the `:runic` namespace is reserved. Runtime resources remain transient. Tests cover failures/retries/hooks, replay without rerunning work, custom-node scheduling, and collection lineage: [SingleOutput tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/single_output_test.exs#L17), [Runner tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/single_output_test.exs#L58), [collection tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/single_output_collection_test.exs#L9). This is a very recent API, merged October 10.

### 3. Persistence acknowledgements and recovery behavior

**Improvements on main, not a new persistence engine.** Workers retain uncommitted events and full values when Store callbacks return failures; checkpoint and persistent stop report failure instead of silently acknowledging success. `Runner.persistence_status/2` exposes saved/pending/error state and acknowledged cursor. Initial build persistence failure prevents dispatch/registration. [Store contract](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic/runner/store.ex#L17), [Runner status/checkpoint API](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic/runner.ex#L391), [failure regression coverage](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/persistence_failure_test.exs#L18).

**Hermitscale value:** make [PostgresStore](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows/postgres_store.ex:67) the persistence extension rather than a second workflow engine. Its transaction currently atomically appends a batch and returns the ending cursor, matching the clarified acknowledgement contract. Ambiguous commit retries still need stable event deduplication at the adapter boundary. Raised DB exceptions follow OTP crash behavior; the retention guarantee concerns returned operational errors while the Worker survives.

Computation completion is explicitly independent of final persistence. [The regression test](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/persistence_failure_test.exs#L179) expects completion notification even after final save failure. Hermitscale's [mark_run_complete](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows.ex:174) currently writes `:complete` in that callback: define whether that means computed or durably saved, and surface the other state. An observer may query status after callbacks return; synchronously calling Worker status from its own callback can deadlock.

Runtime context/policy overrides now apply before pending work recovers, and snapshots omit top-level runtime context. [Recovery tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/runtime_recovery_test.exs#L11). Context APIs themselves already exist locally, and our Credentials module already uses them. Keep resolving fresh credentials on resume. Raw snapshots remain trusted, version-coupled terms and do not sanitize callbacks/resources captured elsewhere.

No background persistence retry loop, outage admission pause, bounded outage buffer, cross-callback transaction, or exactly-once external side effects is provided. Optional fact/payload callbacks support lean storage, but our PostgresStore does not implement them. Snapshot/cursor and hybrid/lazy recovery already existed in the vendor, so they are adoption opportunities rather than entirely new features.

### 4. Failure admission, retry classification, and owned execution

**Main improvements.** Final failures stop admission of new scheduler units for the current evaluation/Worker scope, while already active units can drain. `admission_status/2` distinguishes returned failure from uncertain executor loss; `continue/2` opens another scope once prior work drains. Uncertain work remains ready, so continuing can repeat external effects. Admission causes are Worker-local, not a durable business pause. [Public semantics](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic/runner.ex#L170), [failure tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/failure_admission_test.exs#L67).

`SchedulerPolicy.retry_if` optionally classifies errors with a unary function or MFA. Predicates that raise or return non-booleans fail closed without fallback. Retries remain bounded and local, not durable delayed retries. This would help HTTP rate limiting/transient failures once provider errors stay structured; our [Policy](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows/policy.ex:4) exposes only a subset of upstream policy keys. [Policy semantics](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow/scheduler_policy.ex#L46), [predicate/timeout/fallback safety tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/policy_driver_safety_test.exs#L66).

`owner: pid` and native TaskScope make preview/test work follow caller lifetime; background is still the default. `cancel/2` confirms Worker/native task quiescence when possible, without persisting or undoing external effects. Owned execution is useful for disposable interactive previews; saved business runs should remain background work. Custom executor cleanup has its own contract, and forceful cancellation may bypass it. [Ownership/cancel contracts](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic/runner.ex#L127), [ownership tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/ownership_test.exs#L19).

### 5. Manual dispatch and better inspection

**Manual dispatch is new.** `dispatch_mode: :manual` with `step/2` admits one scheduler unit; a Promise may contain multiple nodes. `continue/2` moves to automatic dispatch. Useful for editor debugging and previews; it is not durable approval/wait semantics and must be passed again after resume. [API](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic/runner.ex#L170), [stepwise tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/stepwise_test.exs#L14).

`component_graph/1` is largely a naming alias for existing `connected_components/1`; `flow_graph/1` provides the compiled projection, exposing generated joins/binders separately from authored relationships. Good for showing editor topology beside execution topology. Structured `Workflow.results/3`, `Runner.get_results/3`, and Mermaid/DOT/Cytoscape serializers already exist in our vendor; use output contracts to simplify terminal result extraction without calling them new features. [Projection tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/workflow/named_connection_test.exs#L284), [result behavior tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/workflow_results_test.exs#L8).

### 6. Compact dispatch foundation

**New low-level opt-in API.** `activation_descriptors/1` and `prepare_for_dispatch/2` permit selecting a limited prefix before context preparation, with explicit in-flight exclusions. FanIn context carries stable batch lookup keys; the coordinator resolves current readiness/ordered values during apply. This matters for large collection workflows. [API limits](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/workflow.ex#L4368), [compact-context/ordered-duplicate tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/workflow/compact_dispatch_test.exs#L10).

Do not promise bounded total memory: source values, fan-out emission, provenance, and accumulator space are outside this bound. The default Worker still [prepares the full frontier](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic/runner/worker.ex#L754) so batching schedulers see all candidates. A custom bounded dispatch design requires its own evidence before adoption.

## Features already present that merit deeper use

The source files for Map, Reduce, StateMachine, FSM, Aggregate, Saga, ProcessManager, ChainBatching, FlowBatch, and GenStage executor are **byte-identical** between the vendor and examined upstream. Their surrounding runtime/identity behavior changed, but these are not newly added components. Standard Rules/Conditions and accumulators can support genuine data-dependent routing/state; existing run context separates credentials/resources from dataflow. HookEvent/Hooks already exist; upstream fixes legacy after-hooks to receive produced Facts and retains construction events created by deferred apply functions.

StateMachine/FSM/Aggregate are plausible selective additions for explicit domain state, approvals, or event-fed coordination; they compile to primitives rather than create a separate runtime. Basic construction/execution/composition are covered in [FSM tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/fsm_test.exs#L141) and [Aggregate tests](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/aggregate_test.exs#L92). The application still owns event ingress, durable wake-ups, validation/authorization, and external-effect idempotency.

Two advertised components need particular skepticism:

- **Saga is not currently a robust per-transaction durable coordinator.** Although its module docs describe individual forward/compensation Rules, the [macro implementation](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic.ex#L1819) builds one Accumulator reducer that runs all transaction callbacks in one invocation; [a test explicitly confirms this](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/saga_test.exs#L445). Compensation iterates [Map.keys of completed results](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic.ex#L2004), without reverse declaration ordering; compensation exceptions are swallowed and the step is marked compensated. Do not use this as the main recovery mechanism for irreversible integrations without fixing/proving these semantics.
- **ProcessManager timeout blocks are not implemented end to end.** The [macro parses timeouts](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/lib/runic.ex#L2821), stores their count, and never passes their duration/body to the constructed accumulator/event rules. The Runner has no ProcessManager timeout scheduling path. The guide's claim that timeout blocks compile into timeout Rules is not substantiated by this code. Explicit application scheduling and ordinary event handlers are needed.

## Breaking changes and adoption gates

1. **Typed SHA-256 identity is the biggest compatibility change.** Generated component/Fact/activation/attempt keys are `Runic.Identity` structs rather than integer hashes. Facts separate payload/content/occurrence identity, preserving equal values at different collection indexes. Use typed keys internally and complete tagged identity strings at boundaries. Runtime context does not affect artifact identity. [Changelog and migration limitations](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/CHANGELOG.md#L10). Arbitrary structs including DateTime/MapSet, PIDs, references, and live functions are not canonical payloads/bindings; explicit projections or portable boundary data are required. Existing native Steps should keep their captured static configuration portable and resources in run context.
2. **No general migration for old durable histories.** Rebuild definition caches; retained old runs need their old runtime or a complete application-specific migration. Converting integer hashes to strings is not such a migration. Audit event/store schemas, internal maps, diagnostics and UI parsing. Our binary event storage can carry structs, but that alone proves neither compatible replay nor key lookup.
3. **Current app compiler calls vendor-only helpers.** `attach_fan_out`, `attach_fan_in`, `regions`, `scope_of`, and `trace` are absent upstream. The new APIs do not make current compilation work unchanged; the patch/architecture assessments own replacement semantics.
4. **Retain explicit base-workflow replay until proven otherwise.** An upstream [persistence failure test](https://github.com/zblanco/runic/blob/6e6373832c00aa9ec5d19faeae945b61e2db50b1/test/runner/persistence_failure_test.exs#L370) states that full Map/Reduce build-log reconstruction has a separate limitation and uses authored topology as the replay base. Hermitscale's [resume implementation](/Users/galdirie/code/hermitscale/lib/hermitscale/workflows.ex:136) recompiles definition JSON and replays against it; do not automatically replace this with bare `Runner.resume/3`. Version the run's authored definition to prevent current graph edits from changing resumed topology.
5. **Retry, skip, and lifecycle semantics warrant application tests.** Failures/uncertain executor loss now have explicit admission boundaries; policy classes stay local; a skipped item is not necessarily a completed collection member. Do not infer join/fan-in completion behavior from happy-path tests. Keep structured status and integration idempotency separate from data values.

Recommendation: first migrate identity/data portability and native Map/Reduce composition in a compatibility experiment; then adopt named bindings and stable component/boundary contracts; then consider SingleOutput and operational controls on the pinned main revision. Preserve application ownership of authorization, editor JSON, expression evaluation, durable schedules, idempotency, and PostgreSQL persistence. Deeper Runic use is valuable where it removes execution bookkeeping, not where a new DSL conceals unverified operational semantics.

## Additional assessment: open PR #43

This section concerns **unmerged code**, not the published release or main. The examined [PR #43](https://github.com/zblanco/runic/pull/43) head is `d1cd8c6863e89d9742bcd54af44c95097064ce4d`; its base includes open [PR #42](https://github.com/zblanco/runic/pull/42) at `6bc647821bef379639dafa56e7b0fa623c83f47a`. Comparing it directly with main therefore mixes the #42 root-scoped failure-suppression fix with #43 execution observation. There are 35 changed files against main and 30 against that #42 base.

### What it adds and why it matters

- `Workflow.execute/3` returns `{updated_workflow, Execution}` for one explicit input occurrence. Managed equivalents are `Runner.start_execution/4`, `execution/3`, `await_execution/4`, and `forget_execution/3`. Admission returns a correlation identity before inline work or Store persistence begins. The new input occurrence keeps repeated equal values distinct. [Immediate API](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow.ex#L3358), [managed admission implementation](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/runic/runner/worker.ex#L287).
- `Execution` separates active units, ready activations, admission state, quiescence, outcomes, failures, and persistence acknowledgement. `Outcome` records completed/failed/skipped/uncertain observations with execution, activation, and attempt coordinates. That is useful for Hermitscale's run detail view and for deciding whether a run computed, failed, or lost its executor; it removes the need to interpret absence of runnable work as success. [Execution model](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow/execution.ex#L1), [Outcome model](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow/execution/outcome.ex#L1).
- Actual acceptance order remains available for audit; consumers can select a stable order by causal depth and activation identity. Stable ordering is within an execution; fresh occurrence IDs can change equal-input sibling ordering across executions. Worker stable admission holds work at the shallowest ready/active causal depth. This is an observable selection policy, not a source-item ordering guarantee or deterministic external completion order. [Ordering and recording](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow/execution.ex#L193), [causal-wave admission](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/runic/runner/worker.ex#L1001).
- The included #42 change persists `ActivationSuppressed` and scopes failed-input suppression to its root, preserving another input's ready work after failure/replay. Skipped nodes still use global downstream suppression. [Failure suppression regression tests](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/test/workflow/failure_suppression_test.exs#L13). Treat the skip limitation as material when retaining/reusing a workflow across inputs.

### Boundaries that affect adoption

1. Observations are process-local and are not reconstructed by stop/cancel/resume. One observed execution can progress at a time in a Worker; adding legacy `run/4` inputs during one is outside the contract. Hermitscale still needs its durable run/event records and fresh credentials on recovery.
2. `Execution.outputs/2` is **not terminal business-output extraction**. It returns accepted completed Runnable results: direct Facts unwrap, while predicate booleans, `:waiting` coordination results and lists of Facts retain shape. Joined/reduced Facts created during coordinator apply remain graph productions. Keep explicit output-port/production queries and execution ancestry filtering where outputs need a per-input boundary. [Source](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow/execution.ex#L202).
3. Quiescent does not mean successful or saved. A stopped execution can retain ready work. An older-input global skip can leave a new scope quiescent/open with no failures but missing expected outputs. An uncertain result says an accepted result was lost, not that the external operation did not happen. Recovery via `continue/2` executes outside the closed observation.
4. Retained observations keep their final persistence snapshot after another scope/input or recovery starts. Query live `persistence_status/2` after later writes/retries. `forget_execution/3` is necessary for long-lived Workers: all scopes otherwise stay in memory. Recording uses `length(outcomes)` and `outcomes ++ [outcome]`, yielding quadratic accumulation per large scope. [Recording source](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow/execution.ex#L110).
5. `await_execution` polls the Worker every 10 milliseconds and respects its caller deadline; it is not a persisted wait or subscription stream. Inline work still prevents snapshots while Worker execution blocks. A zero timeout permits one snapshot query with a 10-ms allowance. [Wait implementation](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/runic/runner.ex#L225).
6. New `ActivationSuppressed` and `ExecutionUncertain` events cannot be replayed by older runtimes. Partial Promise outcomes report the prefix accepted in a reply, not hidden progress lost with the executor. There is no new exactly-once, child invocation, or durable execution-observation store.

### Validation and a directly reproduced gap

The parent research agent executed a focused suite against this PR head using Elixir 1.18.4/OTP 28: **57 tests, 0 failures**. It covered execution observation/outcome/deadline, failure suppression, and stable admission, recorded in [the focused-test log](/tmp/hermitscale-runic-pr43-focused-tests.log). This is narrower than the PR author's reported whole-suite pass on Elixir 1.20.4/OTP 29; do not equate them.

An additional [local probe](/tmp/hermitscale-runic-pr43-eager-probe.exs), with [recorded output](/tmp/hermitscale-runic-pr43-eager-probe.log), found that an eager Rule predicate **starts after an already expired deadline**. A predicate RuntimeError also escapes `Workflow.execute/3` despite `max_retries: 1`, with only one attempted predicate invocation. Source ordering corroborates the gap: [execute applies context and eagerly plans before converting/enforcing execution deadline](https://github.com/zblanco/runic/blob/d1cd8c6863e89d9742bcd54af44c95097064ce4d/lib/workflow.ex#L3393). Thus PR #43 improves observation around accepted work, but does not give all eager predicate callbacks the same timeout/retry/failure envelope as ordinary Step execution. Keep predicates pure, quick, and exception-free by contract; verify upstream handling before offering deadline/retry guarantees for arbitrary predicate work.

**Assessment:** PR #43 makes an idiomatic Hermitscale refactor more attractive by adding a concrete execution observation boundary, while #42 improves multi-input failure isolation. Both are worth tracking and testing. Neither resolves the current compiler's vendor-specific fan-in/fan-out APIs, durable observation reconstruction, terminal result selection, Saga/timeout shortcomings, or effect idempotency. They should be optional experiment targets until merged and application compatibility is demonstrated.
